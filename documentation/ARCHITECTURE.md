# Архитектура и взаимодействие компонентов

## Модули

- **domain/CalendarEvent, EventData**: Данные, статусы, версии, результаты; Не рисует GUI.
- **CalendarService**: CRUD, фильтры, назначения руководителей, ресурсы, история; Не генерирует случайные события.
- **SimulationEngine**: Модельные минуты, сценарии, периодические семинары, команды; Не использует часы ОС или QTimer.
- **ConflictResolver**: Проверяемые варианты времени и помещения; Не изменяет чужие мероприятия.
- **ReminderService**: Курсоры уведомлений по версиям расписания; Не знает о сети.
- **NotificationChannel**: Полиморфный контракт доставки; Не планирует сроки.
- **SimulatedEmailChannel**: Журнал успешной имитируемой доставки; Не отправляет настоящую почту.
- **SimulationReport**: Статистика, снимки, CSV/JSON; Не меняет модель.
- **SimulationStore, JsonCodec**: Проверка файлов, запись, воспроизведение; Не получает доступ к приватным полям календаря.
- **ExperimentRunner**: Серия независимых движков и агрегаты; Не зависит от дисплея.
- **Widget**: Параметры, загрузка, запуск; Не рассчитывает события.
- **SimulationWindow, RunTools**: Управление и представление; Не проверяет конфликты вместо сервиса.
- **OfficeAnimator**: Движение элементов QGraphicsScene; Не продвигает модельное время.

## Связи компонентов

Окно моделирования владеет движком; движок содержит календарь, сервис напоминаний и имитируемый почтовый канал. Поиск вариантов обращается к календарю без мутации. Отчёт читает данные движка, хранилище воспроизводит его публичные команды. ExperimentRunner создаёт один независимый движок для каждого прогона.

Движок владеет сервисами по композиции. NotificationChannel задаёт полиморфный
контракт доставки; QWidget/QObject нужны для GUI. Стратегии конфликтов используют
enum и общий алгоритм поиска вариантов.

Часовые поля окна заполняют CalendarFilter; CalendarService отбирает мероприятия.
Настройки семинара поступают в CalendarSetup, движок создаёт заявку в модельное время.
Назначение проходит через команду движка в CalendarService; SimulationStore
воспроизводит команду, SimulationReport экспортирует назначения.

## Ключевые алгоритмические решения

**Почему интервал полуоткрытый?** Встреча 10:00–11:00 и встреча 11:00–12:00 не конфликтуют.
Проверка пересечения: `a.start < b.end && b.start < a.end`.

**Зачем две версии?** version отражает любое изменение; scheduleVersion меняется при
изменении времени, участников или важности. Для напоминаний важна именно вторая.
Редактирование заголовка не должно запускать новую серию писем.

**Как исключаются дубликаты?** ReminderService хранит следующий срок для пары ID/версия.
После отправки курсор передвигается, поэтому тот же срок не отправится повторно.
При новой версии прежний курсор заменяется, а история доставки остаётся.

**Почему шаг 60 минут не пропускает короткие встречи?** Движок обрабатывает каждую
внутреннюю минуту. Календарь отдельно умеет обрабатывать все переходы в интервале.
QTimer только вызывает step(); часы компьютера не участвуют в расчётах.

**Почему сохранение содержит команды?** Это позволяет восстановить не только таблицу
событий, но и состояния сотрудников, очереди уведомлений, решения и состояние случайного
генератора без дублирующего набора setter-методов. Цена простоты — время воспроизведения
и ограничение совместимости стандартных случайных распределений.

**Чем отказ отличается от конфликта?** Конфликт — причина затруднения, которую можно
устранить переносом. Отказ — окончательный отрицательный результат попытки. Один запрос
может конфликтовать и по комнате, и по людям; общий счётчик конфликтных запросов не
удваивается. В Suggest между конфликтом и новым решением есть ожидание.

**Что показывает занятость?** Долю прошедшего номинального рабочего фонда комнаты,
занятую фактически начатыми мероприятиями. Будущие бронирования в неё не включаются.
Это не прогноз и не доля свободного после ремонта фонда.

**Можно ли доказать, что AutoReschedule всегда лучше?** Нет. Сравнение относится к
демонстрационным параметрам, выбранным seed и полной динамической модели. Решения меняют
состояния и последующие случайные ветви. Исследование показывает результат этих опытов,
не универсальный причинный эффект. Suggest в опытах имеет явно заданного «оператора».

## Изменения относительно исходного состояния

- Подключены ранее не действовавшие настройки напоминаний, стратегий и повторов.
- Добавлены NotificationChannel/ReminderService, заявки, статистика, хранение, эксперименты.
- Планёрки создаёт только динамический пресет.
- Удалена неиспользуемая widget.ui; CMake разделён на core/ui и два executable.
- Исправлены маркеры Git в .gitignore, убраны шаблонные неиспользуемые секции сборки.
- Сохранены календарь, 19 типов событий, роли, архив, ID, анимация, ручной/автоматический
  режим, минимум 5 часов и распределение планёрок по датам.
- Сохранены пользовательские удаления столбцов напряжения/навыка/нагрузки/репутации.
- Проверяются границы входов: 5–9 отделов, до 1000 сотрудников на отдел, 7–30 дней.
- Добавлены ежедневный фильтр часов, периодический шаблон семинаров и явные назначения
  руководителей через сервис. Команды назначения воспроизводятся хранилищем; версия
  генератора новых прогонов — v5, формат состояния — 3. Старые сохранения v4 используют
  прежние правила.
- Все мероприятия доступны независимо от горизонта; сетка ограничена 366 днями для
  сохранения отзывчивости, полный список не обрезает события.

## Проверки

В проекте четыре тестовые цели. Добавлены проверки важности/повторов/дедупликации,
перестроения уведомлений, всех стратегий, устаревшего предложения, отсутствия свободного
времени, ролей, занятости, CSV, сохранения/продолжения, повреждённых файлов, горизонта,
разного размера шага, сброса, агрегатов и передачи настроек/видимости в UI.
Новые проверки охватывают часовые границы и полночь, повторение семинаров, выходные,
конфликт семинара, назначения/переводы руководителей и сохранение этих данных.
Все четыре набора прошли на [Qt 5](../experiments/verification/features-qt5.txt)
и [Qt 6](../experiments/verification/features-qt6.txt).

Основание — предоставленное ТЗ и уточнения пользователя. Имитация почты намеренная;
согласование отмечено в руководстве. Сохранённые 120 экспериментов относятся к v4,
проверки новых функций — к v5.
