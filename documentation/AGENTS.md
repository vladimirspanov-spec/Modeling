# Инструкции для ИИ-агента

## Контекст

Это учебный практикум на C++17 / Qt 6: имитационная модель календаря фирмы. Не превращать его в веб-сервис или production ERP. Документация описывает планируемую систему; не заявлять, что код уже реализован.

Перед работой читать README.md и MODEL.md. Требования исходного задания важнее предложенных значений по умолчанию. При противоречии сообщить пользователю и предложить точечное решение; не менять модель молча.

## Неизменяемые требования

- 5–9 отделов, 7–30 дней, шаг 30 или 60 минут.
- Начальный календарь, добавление и изменение событий, фильтры.
- Проверка конфликтов сотрудников и помещений, права пользователя.
- Напоминания по важности; согласованная имитация email для MVP.
- Архив при удалении из активного календаря; итоговый отчет.
- Движущиеся объекты в UI.
- Объектно-ориентированная структура с осмысленной иерархией.
- Статистические факторы, воспроизводимые эксперименты и документы для отчета.

## Архитектурные правила

- domain/simulation/services не подключают Qt Widgets и не знают о MainWindow.
- GUI — Qt Widgets; сцена QGraphicsScene/QGraphicsView.
- QGraphicsObject и QPropertyAnimation допустимы для визуального перемещения.
- QTimer только вызывает step(); modelTime не вычисляется из wall-clock.
- Одна функция step() для одиночного шага, автоматического и headless-прогона.
- Сохранять порядок внутренних моментов и операций из MODEL.md.
- Состояние меняют сервисы и зарегистрированные команды, не виджеты.
- Данные события и графический объект — разные объекты с общим eventId/employeeId.
- Наследование использовать для стратегий и каналов, композицию — для сущностей.
- Не добавлять HTTP, Docker, PostgreSQL, брокеры, авторизацию по сети без запроса.
- JSON и память достаточны для MVP; не вводить Sql-модуль без необходимости.

## Правила реализации

- C++17; RAII, const, enum class, понятные ID и структуры результатов.
- QObject-владение документировать; не смешивать parent ownership и owning smart pointer для одного объекта.
- QObject использовать только когда требуются сигналы/слоты или свойства.
- Все входы валидировать; ошибки показывать через структурированный результат.
- Интервалы [start,end); нельзя подтверждать конфликтующую заявку.
- Напоминания учитывать внутри шага и дедуплицировать по версии расписания.
- Случайные запросы генерировать независимо от шага и анимации.
- Не использовать случайные ID/реальное время в воспроизводимом модельном журнале.
- Записывать seed и версию генератора; для межплатформенного воспроизведения сохранять поток запросов.
- В реальных письмах, git push, создании удаленного репозитория и иных внешних действиях требуется отдельное разрешение пользователя.
- Не хранить реальные email/секреты в сценариях; использовать фиктивные адреса example.invalid.

## Рабочий процесс

1. Проверить существующий код и состояние репозитория; не перетирать пользовательские изменения.
2. Описать краткий план текущего этапа, не реализовывать весь проект одним несогласованным переписыванием.
3. Сначала модель и тесты, затем UI.
4. После изменения правил обновить MODEL.md; после изменения команд/структуры обновить README.md.
5. Добавить/обновить тесты граничных случаев.
6. Собрать и выполнить тесты, если окружение позволяет.
7. Сообщить измененные файлы, фактически запущенные команды, результаты и ограничения.

Не утверждать «тесты прошли», если они не запускались. Не создавать фиктивные результаты экспериментов; примеры обозначать как примеры. Не писать в документации о реализованных функциях до их появления.

## Сборка и тестирование

Целевой набор команд после появления проекта:

```sh
cmake -S . -B build -DCMAKE_PREFIX_PATH="<Qt kit>" -DBUILD_TESTING=ON
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Qt Test + CTest. В CI без дисплея применять QT_QPA_PLATFORM=offscreen только для GUI-тестов при наличии соответствующего плагина. Модельные тесты не требуют QApplication.

Если Qt отсутствует, прямо сказать об этом; выполнить доступные проверки, не подменять отсутствие сборки догадками.

## Порядок задач

1. CMake, executable SecretarySimulation, тестовая цель.
2. Сущности, SimulationConfig, валидация.
3. CalendarService и ConflictDetector; тесты интервалов и архива.
4. Права и стратегии конфликтов; тесты отказов и переносов.
5. SimulationEngine, журнал и стабильное время.
6. ReminderService и SimulatedEmailChannel.
7. Генератор сценариев и JSON-репозиторий.
8. Qt UI, фильтры и диалоги.
9. Анимация сотрудников и визуальные состояния.
10. Отчет CSV/JSON, серия прогонов, диаграммы и документация.

Каждый этап должен собираться и иметь соответствующие тесты. Допускается изменение порядка при сохранении зависимостей.

## Готовность изменения

- Выполненные требования явно указаны.
- Нет нарушения диапазонов задания и правил MODEL.md.
- Скорость UI не меняет модельный результат.
- События не исчезают из истории.
- Тесты новых правил добавлены; статус запуска честно указан.
- Документация соответствует коду.
- Не появились лишние зависимости и внешние побочные действия.
