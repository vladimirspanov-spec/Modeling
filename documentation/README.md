# SecretarySimulation

Проект практикума: имитационное моделирование системы автоматизации функций секретаря фирмы.

Статус: реализованы окно параметров, CalendarService и календарная сетка с событиями, редактированием, фильтрами, ручным продвижением времени и архивом. Полный движок моделирования с потоком заявок и напоминаниями находится на этапе проектирования. Исходный код UI и CMakeLists.txt находятся в корне проекта, модель и сервисы — в src/.

## Реализованное окно параметров

Executable: `Modeling`. Вкладки: компания и время, сценарий, напоминания, конфликты и эксперимент. Поля заполняются значениями из MODEL.md. Доступны проверка параметров и сброс к значениям по умолчанию. Сводка показывает штат, помещения, период и количество шагов; связанные ограничения проверяются при изменении и по кнопке «Проверить параметры».

Используется фиксированный пресет помещений: комната на отдел и конференц-зал. Начальный календарь создает планерки и недельные совещания либо остается пустым. Параметры случайных заявок, напоминаний, повторов и стратегий переноса предназначены для будущего движка; сейчас конфликтующие операции отклоняются с объяснением. Параметры и события в файл не сохраняются.

Сборка текущего проекта:

```sh
cmake -S . -B build/local -DCMAKE_PREFIX_PATH="<путь-к-комплекту-Qt>"
cmake --build build/local
```

Открыть CMakeLists.txt в Qt Creator и запустить цель Modeling. Интерфейс параметров полностью создается в widget.cpp; widget.ui не используется и исключен из сборки. Кнопка «Открыть моделирование» после проверки параметров открывает календарь на заданный период с выделением рабочих и выходных дней. Окно реализовано в simulationwindow.cpp и получает события из CalendarService.

## Работа с календарем

- «Добавить событие» открывает форму названия, типа, начала/конца, помещения, участников, важности и организатора. Участники задаются существующими ID через запятую; ID распределяются последовательно по отделам.
- Нажатие на карточку открывает сведения и позволяет изменить или отменить запланированное событие в пределах прав пользователя. Начавшиеся и архивные события доступны только для просмотра.
- Пользователь — сотрудник 1 из отдела 1 с ролью из окна параметров. Руководитель имеет полномочия по отделу 1. Секретарь изменяет события всей фирмы; сотрудник может создавать, но не изменять подтвержденные события.
- Фильтры: активный календарь / архив / все события, отдел, ID сотрудника, статус и включительный диапазон дат. Отдел определяется по участникам события. Многодневное событие показывается в каждом затронутом дне.
- «Шаг +30/60 мин» продвигает модельное время. События проходят Planned → InProgress → Completed; завершенные и отмененные уходят в архив. Шаг останавливается на границе периода. Незавершенные и будущие остаются активными.
- Каждый открытый календарь — отдельный прогон в памяти. Закрытие окна освобождает его данные. Экспорт и итоговый отчет еще не реализованы, но архив и история доступны через API сервиса.

## Реализованный сервис и проверки

`src/domain/calendarevent.h` содержит сущности, статусы, фильтры, результаты операций и записи истории. `src/services/calendarservice.h/.cpp` реализует `createEvent`, `updateEvent`, `cancelEvent`, `event`, `calendar`, `history`, `advanceTo`. Данные возвращаются копиями; GUI не может напрямую изменить коллекции. Библиотека `calendar_core` зависит только от Qt Core. `calendarsetup.h/.cpp` создает справочники фирмы и атомарно загружает начальный пресет.

`advanceTo` обрабатывает все старты и завершения внутри интервала, включая события короче шага. Это календарная часть будущего движка, без генератора заявок и напоминаний. Все успешные изменения и переходы сохраняются с модельным timestamp и снимком события. Отказ возвращается структурированным результатом; хранилища отклоненных заявок пока нет.

```sh
cmake -S . -B build/qt6 -DQT_DIR=/usr/lib/x86_64-linux-gnu/cmake/Qt6 -DBUILD_TESTING=ON
cmake --build build/qt6 -j2
ctest --test-dir build/qt6 --output-on-failure
```

Qt Test / CTest: `calendarservice` проверяет модель без QApplication; `calendarwindow` проверяет создание, изменение, отмену, архив, фильтры и передачу параметров через UI с платформой offscreen. GUI-тест сохраняет снимок `modeling-calendar-preview.png` во временный каталог ОС (в текущем окружении `/tmp`).

Целевой комплект — Qt 6; сохранена совместимость сборки с Qt 5. Если CMake ранее выбрал Qt 5, для Qt 6 используйте отдельный каталог и явно укажите пакет. Для системной установки Qt 6 в текущем Linux-окружении:

```sh
cmake -S . -B build/qt6 -DQT_DIR=/usr/lib/x86_64-linux-gnu/cmake/Qt6 -DCMAKE_BUILD_TYPE=Debug
cmake --build build/qt6 -j2
./build/qt6/Modeling
```

## Цель

Исследовать актуализацию календаря, выявление конфликтов и выдачу напоминаний при пошаговом изменении модельного времени. Это локальное desktop-приложение, а не веб-сервис.

Обязательные требования из задания:
- 5–9 отделов.
- Период моделирования 7–30 дней; шаг 30 или 60 минут.
- Календарь с датой, временем, местом, участниками и важностью события.
- Добавление и изменение событий с проверкой конфликтов и прав пользователя.
- Просмотр календаря по фирме, отделу, сотруднику и периоду.
- Напоминания участникам с правилами, зависящими от важности.
- Удаление завершенных событий из активного календаря.
- Итоговый отчет по произошедшим событиям.
- Объектно-ориентированная структура и иерархия классов.
- Движущиеся объекты в интерфейсе.
- Исследование с несколькими наборами параметров, диаграммы и Git-репозиторий.

## Предлагаемый стек

C++17, Qt 6, CMake, Qt Creator. Qt Core — модельные типы, сигналы, JSON; Qt Widgets — интерфейс; Qt Test — тесты. QGraphicsScene/QGraphicsView и QPropertyAnimation — визуализация. Для MVP хранение в памяти и JSON; SQLite и сетевые сервисы не требуются.

Письма в MVP имитируются журналом доставки. Это проектное упрощение: формулировка варианта требует электронную почту, поэтому замену необходимо согласовать с преподавателем. Реальную доставку можно добавить отдельной реализацией NotificationChannel, не меняя движок. Никогда не отправлять реальные письма при массовых экспериментах.

## Интерфейс

1. Параметры: компания, начальный календарь, генератор сценария, напоминания, политика конфликтов, seed.
2. Календарь: таблица/недельное представление, фильтры, карточка события.
3. Моделирование: запуск, пауза, один шаг, сброс, ускорение и текущее модельное время.
4. Сцена фирмы: помещения отделов и конференц-зал; сотрудники движутся к месту события; индикаторы напоминаний и конфликтов.
5. Отчет: показатели, журнал, экспорт CSV/JSON.

Анимация является представлением модельных переходов. Время перемещения не влияет на занятость сотрудника; задержки и транспорт в MVP не моделируются.

## Архитектура и структура

```text
CMakeLists.txt
README.md
MODEL.md
AGENTS.md
src/
  domain/       Department, Employee, Room, CalendarEvent, UserContext
  simulation/   SimulationConfig, SimulationEngine, ScenarioGenerator
  services/     CalendarService, ConflictDetector, ConflictResolver,
                ReminderService, NotificationChannel, SimulatedEmailChannel
  reporting/    RunReport, StatisticsCollector, ReportExporter
  storage/      ScenarioJsonRepository
  ui/           MainWindow, CalendarTableModel, EventDialog, SimulationScene
  app/          main.cpp, ApplicationController
 tests/         Qt Test: model, conflicts, reminders, permissions, integration
 scenarios/     baseline.json, conflicts.json, reminders.json
 docs/          class-diagram.md, class-interfaces.md, experiments.md
```

Domain и simulation не зависят от Qt Widgets. UI обращается к сервисам, а не меняет внутренние коллекции напрямую. Сервисы используют Qt Core по необходимости. Иерархия: NotificationChannel → SimulatedEmailChannel; ConflictResolutionStrategy → RejectStrategy / SuggestStrategy / AutoRescheduleStrategy. Сущности преимущественно связаны композицией; не вводить наследование ради количества классов.

## Этапы реализации

1. Конфигурация и сущности, валидация параметров, JSON-сценарий.
2. Календарь, конфликты, права, архив, unit-тесты.
3. Детерминированный пошаговый движок и напоминания.
4. Генератор случайных операций и автоматические стратегии.
5. UI календаря и управления экспериментом.
6. Движущиеся объекты, отчеты, повторяемые исследования.
7. Диаграмма классов, спецификации интерфейсов, описание модулей и отчет практикума.

## Приемка

- Результат не зависит от скорости анимации и задержек QTimer.
- При одинаковом сценарии, версии генератора и seed повторяется модельный журнал.
- Завершенные события исчезают из активного календаря, но остаются в отчете.
- Несовместимые события нельзя подтвердить без разрешения конфликта.
- Напоминания не теряются при шаге 60 минут и не дублируются.
- Можно завершить прогон без GUI и получить тот же модельный результат.
